# 部署指南

## 部署结构

`docker-compose.yml` 定义三个服务：

| 服务 | 作用 | 对外访问 |
| --- | --- | --- |
| `db` | MySQL 8.4 | 仅 Docker 内部网络 |
| `api` | FastAPI 业务服务 | 仅 Docker 内部网络 |
| `web` | Nginx 静态站点与 API 代理 | `127.0.0.1:8080` |

服务器应另行配置 HTTPS 反向代理，将商户域名和管理域名都转发到 `127.0.0.1:8080`。仓库不包含真实域名、证书或服务器专用配置。

## 部署前准备

- 安装 Docker Engine 和 Docker Compose v2。
- 准备商户端域名与管理端域名，并完成 HTTPS 证书配置。
- 为 MySQL、JWT 和资质加密生成互不相同的强密钥。
- 准备数据库和上传文件的定期备份与恢复方案。

## 配置环境变量

```bash
cp .env.example .env
```

必须修改的变量：

| 变量 | 说明 |
| --- | --- |
| `MYSQL_PASSWORD` | 应用数据库用户密码 |
| `MYSQL_ROOT_PASSWORD` | MySQL root 密码，不应与应用用户密码相同 |
| `JWT_SECRET` | JWT 签名密钥，至少 32 个字符 |
| `CREDENTIAL_ENCRYPTION_KEY` | 资质文件加密密钥，至少 32 个字符且不得与 JWT 密钥相同 |
| `CORS_ORIGINS` | 两个 HTTPS 入口的完整 Origin，逗号分隔 |
| `DEMO_OPERATOR_PASSWORD` | 空数据库初始化演示运营账号的密码 |
| `DEMO_MERCHANT_PASSWORD` | 空数据库初始化演示商户账号的密码 |

可选变量：

- `CREDENTIAL_ENCRYPTION_PREVIOUS_KEYS`：轮换加密密钥时用逗号分隔的历史密钥。
- `JWT_EXPIRE_MINUTES`：会话有效期，默认 480 分钟。
- `LOGIN_ATTEMPTS_PER_MINUTE`：应用层每分钟登录尝试限制。
- `VITE_ICP_NUMBER`、`VITE_PUBLIC_SECURITY_NUMBER`、`VITE_PUBLIC_SECURITY_CODE`：前端构建时注入的备案信息。

不要将 `.env` 提交到 Git。

## 首次部署

### 1. 构建镜像并启动数据库

```bash
docker compose build
docker compose up -d db
docker compose ps
```

等待 `db` 健康检查通过。

### 2. 执行数据库迁移

```bash
docker compose run --rm api alembic upgrade head
```

生产模式不会在应用启动时自动建表，因此这一步不能省略。

### 3. 启动全部服务

```bash
docker compose up -d
docker compose ps
curl --fail http://127.0.0.1:8080/api/v1/health/ready
```

预期三个服务均为运行或健康状态。

## 健康检查

| 地址 | 检查内容 |
| --- | --- |
| `/healthz` | Nginx 容器是否可响应 |
| `/api/v1/health/live` | FastAPI 进程是否存活 |
| `/api/v1/health/ready` | 数据库是否可查询、上传目录是否可写 |

查看日志：

```bash
docker compose logs --tail=200 api
docker compose logs --tail=200 web
docker compose logs --tail=200 db
```

Compose 已将每个容器的 JSON 日志设置为单文件 10 MiB、最多保留 5 个文件。

## 反向代理要求

- 两个公网入口都转发到 `127.0.0.1:8080`。
- 必须使用 HTTPS，并将原始 `Host` 和正确的客户端 IP/协议信息传给内层 Nginx。
- 商户入口的最左侧子域名为 `merchant`，管理入口为 `admin`；否则内层 Nginx 无法生成入口角色头。
- 只向公网开放 80/443，不向公网暴露 MySQL 或 API 容器端口。

## 数据与备份

需要持久化和备份的两类数据：

- `mysql_data` Docker 卷：业务数据库。
- `uploads_data` Docker 卷：商品图片和入驻资质文件。

数据库与上传文件必须使用同一个业务时间点的备份恢复，否则可能出现数据库记录和文件不匹配。

`/var/lib/wst2-status/latest.json` 只用于向 API 提供最近备份状态，它不是备份本身。当前 Compose 不包含自动备份作业，需由服务器定时任务或外部备份系统实现。

## 更新部署

1. 先完成数据库与上传文件备份。
2. 获取已经评审的代码版本。
3. 构建新镜像。
4. 执行 Alembic 迁移。
5. 启动新容器并执行健康检查。

```bash
docker compose build
docker compose up -d db
docker compose run --rm api alembic upgrade head
docker compose up -d
curl --fail http://127.0.0.1:8080/api/v1/health/ready
```

回滚应优先使用已验证的旧镜像和部署前备份。不要在未评估数据丢失的情况下盲目执行 Alembic `downgrade`。

## 生产检查清单

- [ ] 所有 `.env` 占位值已替换。
- [ ] JWT 密钥、资质加密密钥和数据库密码互不相同。
- [ ] `CORS_ORIGINS` 只包含真实 HTTPS 入口。
- [ ] 商户端与管理端域名、HTTPS 和 DNS 均已验证。
- [ ] Alembic 已升级到 `head`。
- [ ] `health/ready` 返回就绪。
- [ ] MySQL 未对公网开放。
- [ ] 数据库和上传卷的定期备份、异地保存和恢复演练已配置。
- [ ] 监控、日志告警和访问控制已配置。
- [ ] 公开环境中只使用虚构演示数据。
